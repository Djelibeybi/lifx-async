<objective>
Ship a CI guard that counts for itself whether a pull request's changed measured lines were
scored, and fails the build when they were not.

Purpose: on PR #208 the `codecov/patch` status reported success against zero scored lines and
nothing objected. The evidence gathered during the spec does not support the recorded cause, so
this guard is cause-agnostic by design: it computes both sides from the repository's own data and
treats Codecov's own report of itself as a cross-check that can never decide the build.

Output: `.github/patch_coverage_guard.py`, a fixture-driven test suite that exercises every
branch locally with no pull request, and a step in the ubuntu test job that runs it.
</objective>

## Cross-AI review revisions

`15-REVIEWS.md` found one blocking defect in this plan and three smaller ones.

**HIGH, fixed.** The changed-line computation had a false-pass case that contradicted this
phase's own locked acceptance. The earlier definition dropped every changed line absent from an
*existing* file entry's `executable_lines`, so a report that contained the changed file but
classified none of its changed lines produced `changed_measured == 0` and the guard passed.
`15-SPEC.md` R4 locks the opposite outcome. That definition also happened to be what protected a
docstring-only change from being read as a vacuous gate, so the two requirements pulled in
opposite directions and had to be reconciled rather than patched separately.

<assumption_delta_decision>
  <primary_noun>the authoritative executable-line set for a changed measured file</primary_noun>
  <decision>promote</decision>
  <rationale>It changes from derived, read out of the coverage report being judged, to chosen,
  computed independently from coverage.py's own analysis of the checked-out file under the
  project's coverage configuration. A gate may not take its own denominator from the artefact it
  is auditing, which is exactly how a report that classifies nothing scored a pass.</rationale>
</assumption_delta_decision>

The reconciliation is a single source that satisfies both requirements at once. Reading a file
with `Coverage(config_file="pyproject.toml").analysis2(path)` returns the statement line numbers
coverage.py's own parser found, with the project's `[tool.coverage.report] exclude_lines` already
removed. Verified against this repository before writing this revision, on coverage 7.15.0:
module and function docstrings are not statements, comments and blank lines are not statements,
and `if __name__ == "__main__":` together with its body is reported as excluded and is absent
from the statement set. So the docstring-only case still yields an empty changed measured set and
still passes, while a report that omits a real statement can no longer shrink the denominator to
make itself look complete. Task 2 gains the fixture that reaches the previously unreachable case.

**MEDIUM, not adopted, with reasoning.** The review asked for the guard step to run before the
Codecov upload steps so the `codecov/patch` cross-check has more time to settle. It stays where
D-06 puts it, immediately after `Upload coverage to Codecov`, for three reasons. First, D-06 is a
locked decision and this is a targeted revision pass, not a replan. Second, moving earlier would
not help the cross-check at all: `codecov/patch` is computed once Codecov has merged the uploads
from every matrix cell, so running the guard before this cell has even uploaded makes a pending
status more likely rather than less. Third, the independence concern the suggestion also carries,
that a failing Codecov upload would skip the authoritative check, is already answered: the guard
step's `if:` contains `!cancelled()`, so it runs even when an earlier step in the job failed. The
honest characterisation, now recorded on the step itself, is that the live cross-check is
best-effort and a pending result is the expected common outcome. The divergence evidence R5 wants
does not depend on it, because the recorded `d68d36a` and `0be78e6` descriptions are replayed
from fixtures through `--status-json`, with no network and no pull request.

**LOW, not adopted, with reasoning.** The review suggested `defusedxml` for the Cobertura parse.
Rejected and already recorded as an accepted risk at T-15-14: `xml.etree.ElementTree` does not
resolve external entities, the document is produced by pytest-cov in the same job rather than
supplied by a contributor, and the project ships zero runtime dependencies. Only one of the three
reviewers raised it. The acceptance stays visible in the threat register rather than being silent.

**LOW, fixed.** `.github/check_patch_coverage.py` is now added to `[tool.pyright] include`
alongside the guard, and `--head` is validated before it reaches the `gh` argument vector.

## Plan-checker revision: the collection gates read the wrong output format

Task 2's two `--collect-only` gates searched for a text shape this project's own configuration
never emits, for the same reason recorded against plan 15-01 as T-15-42. `addopts` begins with `-v`
and pytest verbosity is cumulative, so `pytest --collect-only -q` ran at net verbosity 0, where
`--collect-only` prints the indented `<Module>` and `<Function>` tree rather than node ids. The
test-count gate could never reach any threshold and always failed. The negated gate asserting the
guard's tests stay out of the default run was worse: it passed while searching text that could not
have contained a match, and it is the only check that this phase's own tooling suite is opted out
rather than silently added to every developer's default run.

Both commands now carry two `-q` flags and a positive control that asserts the output really is
node ids before any count or match is trusted. Neither passes `--tooling`, and neither may:
naming a path under `.planning/scripts/tests/` means pytest never loads `tests/conftest.py`, which
is where the flag and the deselection hook live, so the marked items are collected without opting
in and the flag would be rejected as an unrecognised argument. That was measured rather than
reasoned: `uv run --frozen pytest scripts --collect-only -q -q --disable-emulator` exits 4 on an
option registered only in `tests/conftest.py`.

The `>= 25` threshold is replaced by `>= 26`, counted over distinct test functions rather than over
collected items. The old figure was a running tally carried across three revision rounds against a
command that could never report a real count, so it was never reconciled with the behaviour list;
counting that list as it now stands gives 26. Counting distinct test functions matters because a
parametrised test contributes several items and would otherwise lift the figure past the floor
while a scenario went uncovered: measured on this tree, a parametrised library module collected 68
items for 37 distinct test functions. Recorded as T-15-43.

**Deriving its own changed set.** The guard takes `--base` and computes
`merge_base = _run_git(["merge-base", validate_base(args.base), "HEAD"]).strip()` itself, then
calls `diff_added_lines(merge_base)` with no `sources` argument. It never accepts a `--source`
option, so it cannot inherit `check_patch_coverage.py`'s silent-skip gap where a changed file
absent from the passed list is skipped.

`--head` gets the same treatment as `--base`. It is interpolated into the `gh api` argument
vector, so pass it through `validate_base` before it is used, exactly as `--base` is. List argv
with no shell already makes injection impossible, but the validator is imported anyway and an
unvalidated SHA reaching an external command is a habit worth not forming. An invalid `--head`
exits 2 as an operational error, before any subprocess runs.

**The measured-tree rule as data.** Three module constants encoding SPEC R3:
- `MEASURED_PREFIXES = ("src/lifx/",)`
- `MEASURED_FILES = ("scripts/generate_theme_data.py",)`
- `UNMEASURED_PATHS`, the four entries of `[tool.coverage.run] omit`:
  `src/lifx/protocol/generator.py`, `src/lifx/protocol/protocol_types.py`,
  `src/lifx/products/generator.py`, `src/lifx/theme/data.py`.
A repository-relative POSIX path is measured when it ends in `.py`, is in `MEASURED_FILES` or
starts with a member of `MEASURED_PREFIXES`, and is not in `UNMEASURED_PATHS`. Everything else,
including `tests/`, `codecov.yml`, `uv.lock`, `.github/**`, `.planning/**`, `docs/` and any
non-Python file under a measured prefix such as `src/lifx/py.typed`, is unmeasured. The `.py`
condition is not decoration: the authoritative statement set below is produced by a Python source
analyser, which cannot answer for a file that is not Python.

**Cobertura adapter.** `load_coverage_xml(path, repo_root)` parses the report with
`xml.etree.ElementTree` and returns `dict[str, CoverageEntry]` keyed by repository-relative
POSIX path, so the rest of the guard works in the same shape `check_patch_coverage.py` uses.
Two details decide correctness here:
- coverage.py writes one or more `<sources><source>` roots and then `<class filename="...">`
  values relative to a root. With this project's src layout and `--cov=lifx`, a filename reads
  `lifx/api.py` under a source root that ends in `src`, so the guard must join each candidate
  root to the filename, resolve, and take the result relative to `repo_root`. Try each source
  root in order and take the first that resolves to an existing path under `repo_root`. Skip a
  candidate that resolves outside `repo_root`; that is a path-traversal refusal, not a fallback.
  If no root resolves, fall back to the filename normalised as a POSIX path.
- Cobertura carries no notion of an excluded line and no branch arcs, so build each
  `CoverageEntry` with `executed_lines` from `<line>` elements whose `hits` attribute is above
  zero, `missing_lines` from those whose `hits` is zero, and empty frozensets for
  `excluded_lines`, `executed_branches` and `missing_branches`. The guard only asks whether a
  line is classified at all, which `CoverageEntry.executable_lines` answers exactly.
- Reading XML is the one place untrusted-looking input is parsed. The file is produced by
  pytest-cov in the same job, so the disposition is to accept it with a Bandit suppression
  comment stating that provenance, not to add a parser dependency to a zero-dependency project.

**The authoritative statement set.** `authoritative_statements(repo_root, path)` returns the set
of line numbers coverage.py considers executable statements in the checked-out file, taken from
the source rather than from the report:
`coverage.Coverage(config_file=str(repo_root / "pyproject.toml")).analysis2(str(repo_root / path))`
returns a five-tuple whose second element is the statement set and whose third is the excluded
set. Take the second. It already has the project's `[tool.coverage.report] exclude_lines` removed,
which is why the excluded set is returned separately and is not needed here. Build the `Coverage`
object once per run and reuse it across paths; `analysis2` needs no coverage data file, which was
confirmed against this repository on coverage 7.15.0 before this plan was written.

The config file is not optional and its absence is not a soft failure. Constructing
`Coverage(config_file=...)` on a path that does not exist raises immediately, confirmed on the
same version with `ConfigError: Couldn't read '...' as a config file`. Construct the object once
inside a `try` and turn any `coverage.exceptions.CoverageException` raised there into an exit-2
operational error naming `repo_root / "pyproject.toml"`. Without the project's configuration the
`exclude_lines` list would not apply and the guard would count configured exclusions as changed
measured lines. That is a false failure rather than a false pass, but it is still wrong and it
must not happen quietly.

Two coverage.py exceptions matter and must be handled distinctly, because collapsing them would
turn a real defect into a pass. `coverage.exceptions.NoSource` means the file is not on disk:
print a warning line naming the path, contribute nothing for it, and continue. Any other
`coverage.exceptions.CoverageException`, including `NotPython` on a file that cannot be parsed,
is an operational error and exits 2. Never treat either as an empty statement set that quietly
shrinks the denominator.

**The count.** `measured_changed_lines(added, report, repo_root)` walks the added lines grouped by
path via `_added_numbers`, keeps only measured paths, and for each one intersects its added line
numbers with `authoritative_statements(repo_root, path)`. That intersection is the file's
contribution to `changed_measured`. It is deliberately computed from the source and never from
`report`, which is the artefact under judgement: a report that omits a statement must not be able
to remove that statement from the count it is being measured against.

`scored` is then the subset of `changed_measured` that the report actually classifies:
- when the report has an entry for the path, `scored` gains the changed measured lines that
  intersect `entry.executable_lines`;
- when the report has no entry for the path, or has an entry that classifies none of those lines,
  nothing is added to `scored` for it. Both shapes now reach the same outcome, which is the point.

This definition satisfies two requirements that pull in opposite directions, and it satisfies them
with one mechanism rather than two special cases:
- a docstring-only, comment-only or blank-line-only change to a measured file still passes,
  because coverage.py's parser counts none of those as statements, so the intersection is empty
  and `changed_measured` is zero. The same holds for a change confined to a configured exclusion
  such as an `if __name__ == "__main__":` block, which `analysis2` removes from the statement set;
- a report containing the changed file but classifying none of its real changed statements now
  fails, because those statements are in `changed_measured` on the source's authority and in
  `scored` on nobody's. Under the previous, report-derived definition this case computed
  `changed_measured == 0` and passed, which contradicted SPEC R4's locked acceptance.

**The decision.**
- `changed_measured == 0`: pass. Print `PASS: no changed measured lines` and the file counts.
  This is the tests-only, `codecov.yml`-only, `uv.lock`-only and `ci.yml`-only case.
- `changed_measured > 0 and scored == 0`: fail. Raise `VacuousGateError` and exit 1. The message
  must contain the literal marker `VACUOUS COVERAGE GATE` and the two counts in the form
  `changed_measured=N scored=M`, followed by the measured paths the report did not contain.
- `0 < scored < changed_measured`: pass with a warning line containing `WARNING: partially scored`
  and the same two counts. The guard does not enforce a fraction; `codecov/patch` remains the
  enforcer of the 100% target.
- `scored == changed_measured`: pass.
