## Execution ordering

This plan is wave 3 and depends on both 15-01 and 15-02. The 15-02 dependency is a working-tree
dependency rather than a code one. Plans execute in one shared worktree, and 15-02's tasks 1 and 2
deliberately leave the suite red until its task 3 closes the window. Every observation this plan
records is a pytest run whose meaning is the process's exit behaviour, so a red tree caused by a
half-finished relocation would contaminate the evidence with a failure mode that has nothing to do
with the coordinator teardown. It would also make the recorded run unrepeatable, which defeats the
point of committing the runner and the patch. Waiting for a green tree is what makes the two runs
comparable to each other.

argument-parsing style of a standalone maintainer script is also a 15-02 artefact, so the same
dependency covers it. Its PEP 723 header is deliberately not copied: this runner has none, because
its child must import the project's test stack.

This plan shares wave 3 with 15-03 and the two touch no file in common: 15-03 owns
`.github/`, `.github/workflows/ci.yml`, `pyproject.toml` and the guard's tooling test, while this
plan owns three phase artefacts, `deferred-items.md` and `STATE.md`. Every pytest invocation here
is scoped to `tests/test_network/test_discovery_coordinator.py` or to a single node id, and every

## Cross-AI review revisions, round 2

Round 2 called this the strongest plan of the five and then found two ways it could record
evidence that did not happen. Both are fixed, along with four smaller items.

**HIGH, fixed: the observer could record a failed pytest run as a clean exit.** The child was
instructed only to call `pytest.main(...)`, with the return value discarded, so the child process
exits 0 whatever pytest reported. Reproduced twice, by the reviewer and again by the orchestrator:
with the return discarded, `pytest.main(["tests/does_not_exist.py::nope", "-q"])` leaves the child
exiting `0`, while `raise SystemExit(pytest.main([...]))` on the same invocation exits `4`. Process
exit *is* the evidence signal in this plan, so a mistyped node id, a collection error or an
outright test failure would have been written into the record as a clean teardown, and the
conclusion drawn from it would have been about a run that never happened. The child now ends with
`raise SystemExit(pytest.main([...]))`, and Task 1 gains a negative control that observes a
deliberately invalid node id and requires the recorded child exit code to be non-zero.

**HIGH, fixed: the required `--output` argument was missing from the plan's own invocations.** The
runner was specified as taking an output path, and neither the Task 1 verification invocation nor
Task 2 passed one, so either argument parsing would have failed at the first verify or the
"required" argument had an undocumented default. Task 3 was then told to consume two records with
no filenames. Both records now have explicit, committed paths named in this plan, and `--output` is
passed in every invocation.

The two records become tracked phase artefacts rather than temporary files. They are redacted at
capture, so committing them is safe, and it means the evidence document cites a machine-readable
record that survives an interruption between Task 2 and Task 3 rather than a file in a temporary
directory that may not.

**MEDIUM, fixed: an expected-zero gate exited non-zero exactly when it passed.**
`git worktree list --porcelain | grep -c 'TEST-02'` prints `0` and exits `1` when the cleanup
succeeded, which is the pass case. Confirmed locally. It is rewritten to
`test "$(... | grep -c ... || true)" -eq 0`. The two-file `grep -c` gates in Task 3 had a milder
version of the same problem in the other direction: `grep -c` over two files exits 0 if either
matches, so a record that cited the evidence file in one of the two records and not the other
would have passed on exit status alone. They are now asserted per file.

**LOW, fixed: patch generation put the defective form in the main working tree.** The action said
to make the edit, run `git diff > <patch>`, then revert, while `T-15-18` claims the defective form
is applied "only inside a `git worktree` scratch checkout". The two disagreed about where the
defect lives, even if only for a moment and under a single executor. The diff is now generated
inside the scratch worktree, so the mitigation text is literally true.

**LOW, fixed: the no-absolute-path acceptance greped three prefixes.** `/Users/`, `/home/` and
`/Volumes/` do not cover a macOS scratch worktree, which lives under `/var/folders/...`. The
four-root replacement in the runner covers it, because the worktree root is replaced before any
write, so this was backstop coverage rather than a leak. The backstop is now a general scan for a
delimited token that begins with a slash and holds at least two path segments, which matches
`/var/folders/...` and does not match a URL, a relative node id or a `<repo>`-placeholder path.

**LOW, fixed: the instruction to kill the child on timeout was not implementable.**
`subprocess.run(..., timeout=...)` already kills the child and waits for it before raising
`TimeoutExpired`; there is no handle to kill afterwards without switching to `Popen`. The action
now relies on that documented cleanup and keeps only the parts that are implementable: recording
which of the two bounds fired and the elapsed time actually measured.

**Worktree creation failure, adopted from Antigravity.** Task 2 now names the recovery when
`git worktree add` fails because a directory or a stale registration survives an earlier aborted
run, rather than leaving the executor to improvise at the one point in this plan where improvising
means editing worktree state by hand.

Write `.planning/phases/15-coverage-gate-and-test-suite-health/15-TEST-02-observe.py`, a
stdlib-only script with **no PEP 723 header**, then run it against the current tree and keep the
output.

**Why no header, and how it is invoked.** The child interpreter has to import pytest, `lifx` and
the project's plugin stack. `uv run` on a script carrying an inline metadata header resolves that
header into an isolated environment, so a header naming no dependency gives the child an
interpreter with none of them, and the first observation dies at `import pytest`. This was
reproduced before the plan was written: a header-carrying script with `dependencies = []` ran
under a `~/.cache/uv/environments-v2/...` interpreter and raised
`ModuleNotFoundError: No module named 'pytest'`, while `uv run --frozen python` in this project
resolved pytest 9.1.1 and `lifx` from `.venv`. Declaring the whole test stack in a header instead
is the other available option and is rejected: it would duplicate the dev dependency group, would
resolve separately from `uv.lock`, and would need its own resolution again inside the scratch
worktree. So the runner has no header and every invocation is
`uv run --frozen python .planning/phases/15-coverage-gate-and-test-suite-health/15-TEST-02-observe.py ...`,
which makes `sys.executable` the synced project interpreter and the child a subprocess of it.
Write that invocation into the module docstring, so the file states how it must be run.

**Interface.** The runner takes four arguments: `--node`, the pytest node id to observe;
`--timeout`, the watchdog in seconds; `--output`, the path the record is written to; and
`--repo-root`, the directory the observation runs in. `--repo-root` defaults to the current
working directory. `--output` has **no default**: make it a required argument and let argparse
reject an invocation that omits it. A defaulted output path is how two observations end up
overwriting one file, or writing somewhere Task 3 does not look, and this plan's whole product is
two records that can be told apart. Every invocation in this plan and in Task 2 passes `--output`
explicitly, to the committed paths named below.

The child is launched with `cwd=repo_root` and `[sys.executable, "-c", ...]`, so the interpreter is
the environment the runner itself was started in and the code under observation is whichever
checkout `--repo-root` names. That separation is what lets one runner file observe both the main
tree and Task 2's scratch worktree.

**The child propagates pytest's return code, and this is the single most load-bearing line in the
runner.** The child arms `faulthandler.dump_traceback_later(timeout, exit=True)` before importing
pytest, then ends with:

`raise SystemExit(pytest.main([node, "--no-cov", "-p", "no:cacheprovider"]))`

Not a bare `pytest.main(...)` call. In this plan the child's exit code *is* the evidence: a zero
exit means the process terminated cleanly, which is the claim the whole experiment is built to
support. `pytest.main` returns its exit status rather than raising, so discarding the return value
leaves the child exiting 0 no matter what pytest reported. That was reproduced twice while revising
this plan: with the return discarded, `pytest.main(["tests/does_not_exist.py::nope", "-q"])` prints
a collection error and the child still exits `0`; wrapped in `raise SystemExit(...)` the same
invocation exits `4`. A mistyped node id or a genuinely failing test would otherwise be written
into the record as a clean teardown, and the conclusion drawn from it would describe a run that
never took place. Put a comment on that line saying so, because it looks like a stylistic choice
and is not.

Arming the watchdog inside the child is the other half of the same point: the recorded failure mode
happens after the test reports, inside `threading._shutdown` awaiting
`concurrent.futures.thread._python_exit`, so the suite's own `timeout = 60` with
`timeout_method = "thread"` can never fire on it, and a parent process cannot dump a child's
threads.

The parent additionally wraps the child in `subprocess.run(..., timeout=watchdog + 30)` as a
backstop, so a child that cannot even dump is still bounded. Handle `subprocess.TimeoutExpired`
explicitly: record that the parent backstop fired rather than the in-child watchdog, and record the
elapsed time actually measured. Do not write code that tries to kill the child in that handler.
`subprocess.run` already kills the child and waits for it before raising `TimeoutExpired`, and it
hands the caller no process object to act on, so a kill there is unreachable without switching to
`Popen`. `Popen` is not worth the extra failure surface for a bound that exists only as a backstop
to a backstop. Rely on the documented cleanup and record which bound fired, which is what makes an
honest record on a platform where terminating a blocked child is slow.

**A negative control, so the exit-code contract is demonstrated rather than asserted.** After the
real observation, run the runner once more against a deliberately invalid node id,
`tests/test_network/test_discovery_coordinator.py::test_this_node_does_not_exist`, writing to a
throwaway path under `${TMPDIR:-/tmp}`. The recorded child exit code must be non-zero. That single
run is what distinguishes a runner that propagates pytest's verdict from one that reports every
invocation as clean, and it is cheap: a collection error returns in about the same time as the
test itself. Record the negative control's exit code in the plan summary. Do not commit its
record; it is a proof about the instrument, not evidence about the coordinator.

Use a watchdog of 60 seconds. The test's observed runtime is 0.02 seconds, so 60 is three orders
of magnitude above it and cannot be mistaken for a tight budget (SPEC R6's timeout boundary).

The runner records, as JSON and as human-readable text: the exact child argument vector, the
resolved `--repo-root`, the commit SHA that directory is at, read with
`git -C <repo_root> rev-parse HEAD`, whether that directory has uncommitted changes to the
observed test file, the watchdog value, the parent backstop value, which of the two bounds fired
if either did, the child exit code, the elapsed wall time measured with `time.monotonic()`,
whether a `Timeout (...)!` faulthandler banner appeared, the tail of the child's captured stderr,
and `platform.platform()` plus `platform.python_version()`. Recording the working directory and its
SHA is what makes a record produced inside the scratch worktree self-evidently that, rather than
something a reader has to take on trust.

**Preserve stderr unconditionally, not only when a bound fires.** Task 2's evidence has to
distinguish two different causes of a non-zero child exit: the hang the experiment is looking for,
and an ordinary test failure in the patched form. The plan's rule is that a hang carries a
faulthandler banner or a fired bound and a plain failure carries neither, which makes the plain
failure a verdict reached from the *absence* of two signals. That is only usable if the record also
carries what pytest actually said. Capture the child's stderr, redact it with the same four-root
replacement as everything else, keep its last 4000 characters under a `stderr_tail` field, and write
it whatever the exit code was, including zero. The faulthandler banner detection reads the same
captured text, so nothing extra is captured for this; what changes is that the text is retained in
the record rather than only scanned and discarded.

Before writing anything, rewrite every absolute path in the captured output: the repository root
becomes `<repo>`, the scratch worktree root becomes `<worktree>`, the virtual environment root
becomes `<venv>`, and the user home directory becomes `<home>`. Captured tracebacks carry absolute
paths that include account and volume names, and the repository's privacy rule binds committed
artefacts, so redaction happens in the runner rather than by hand afterwards.
