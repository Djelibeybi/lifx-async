<objective>
Give callers a typed Move builder, `MultiZoneEffect.move(direction, speed, duration=0)`, that
encodes the eight-slot `parameters` list internally, while the raw `MultiZoneEffect(...)` path Home
Assistant ships today stays byte-for-byte identical.

Purpose: EFFECT-01 R4 and R6, plus the builder half of R7. Issue #191 asked for this after the
Home Assistant core migration review found `parameters=[0, int(direction), 0, 0, 0, 0, 0, 0]`
sitting outside the library.

Output: `_coerce_direction()`, `MultiZoneEffect.move()`, the widened `direction` setter, and a new
`tests/test_devices/test_multizone_move.py` holding the golden-packet backstop and the verbatim
docstring-example harness that plans 06 and 07 extend.

**The emulator this phase runs against.** `uv.lock` pins lifx-emulator-core **3.7.0** and
`pyproject.toml` admits `>=3.1.0`; this phase bumps nothing and adds no Thread emulation. Every
emulator claim below was re-verified by the planner against the installed 3.7.0 package
(`uv run --frozen python -c "import lifx_emulator, os; print(os.path.dirname(lifx_emulator.__file__))"`)
and against a live in-process 3.7.0 server on 2026-09-23.

**Why direction is asserted on the received packet, not on get_effect().** In 3.7.0,
`SetEffectHandler` (`handlers/multizone_handlers.py`) stores only the Move effect type and
`packet.settings.speed // 1000` (whole seconds), and `GetEffectHandler` hard-codes all eight
parameter slots to 0 in its `MultiZoneEffectParameter(parameter0=0, ...)` block. Measured: after
`set_effect(MultiZoneEffect(FirmwareEffect.MOVE, 5000, parameters=[0, 1, 0, 0, 0, 0, 0, 0]))`,
`get_effect()` reports MOVE, speed 5000, parameters all 0 and therefore `Direction.REVERSED`,
while the `MultiZone.SetEffect` captured at the emulated device carries `settings.type == MOVE`,
`settings.speed == 5000` and `settings.parameter.parameter1 == 1`. The emulator tests here
therefore read the effect type and speed back through `get_effect()` (whole-second speeds only)
and read the direction from the received packet. That is the acceptance mechanism the amended
18-SPEC R5 states (per the maintainer adjudication at L540@92a657d), and the SPEC names the same
locked 3.7.0 release. The executor does not edit the SPEC. When a later emulator release
round-trips Move parameters, the packet capture can be joined by a `get_effect()` direction
assertion; nothing else here changes.

**How packets are captured on 3.7.0.** The emulator runs in a background thread
(`EmulatorRunner` in `tests/conftest.py`). `EmulatedLifxServer.get_device(serial)` returns the
`EmulatedLifxDevice` the server routes to, and `_process_device_packet()` calls
`device.process_packet(header, packet)` positionally for every packet a scenario does not drop.
Wrapping that bound method with `patch.object(..., wraps=...)` records each received packet in
arrival order. One ordering trap, verified in `server.py`: for an acknowledged SET the server
sends its fast-path ack **before** calling `process_packet()`, and `connection.request()` returns
`True` on that ack, so a capture closed straight after an awaited SET can miss it. Every capture
block therefore ends with a request-response round trip to the same device (`get_effect()`) before
it closes; datagrams are handled in arrival order on the emulator's loop, so that reply proves
every earlier packet was processed.

**Two contract decisions settled here rather than at execution time.** Non-numeric `speed` or
`duration` raises `TypeError`, not `ValueError` (see must_haves; review L102@92a657d). The
`direction` property's getter keeps `-> Direction | None` and its setter takes `Direction | str`;
pyright 1.1.411 in this project's standard mode accepts that asymmetric shape with 0 errors
(review L103@92a657d).

**The conversion.** Add module-private `_UINT32_MAX = 2**32 - 1` and `_UINT64_MAX = 2**64 - 1`
and a private staticmethod `MultiZoneEffect._seconds_to_units(value: float, per_second: int,
maximum: int, name: str) -> int`, in this order:
  1. Raise `TypeError` when `value` is a `bool` or is not an `int` or `float` instance (check
     `bool` first, since it subclasses `int`), with a message naming the field, saying it must
     be a number of seconds, and naming the rejected type; this is the deliberate runtime
     contract for non-numeric input (review L102@92a657d), so no later step sees a string or

     `OverflowError` ("int too large to convert to float"), which would escape the promised

     Python).

     `OverflowError` (also verified by the planner). An `int` scales exactly with no float
