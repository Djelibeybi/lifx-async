<objective>
Follow the LIFX app when Morph starts without a palette: animate the colours already on the
device, and generate a three-colour palette only when the device shows a single colour.

Purpose: EFFECT-02 R10 and the shared helper R9 reuses (D-13 to D-19, D-22, D-23; folded in from
the former Phase 17.1). Today Morph with no palette sends `palette_count=0` and sixteen zeroed
slots and leaves the firmware to decide, which on a single-colour device shows no visible Morph.

Output: `derive_effect_palette()` and `validate_effect_palette()` in `component_state.py`, the
MORPH-only derivation step in `MatrixLight.set_effect()`, golden payload tests captured before the
change (immutable afterwards), and the two existing matrix tests that asserted the old
unconditional behaviour updated, in the same commit as the derivation, to state which device
condition they cover.

**The helper's module.** D-22 names `component_state.py`, next to `is_dark()` and `hsk_matches()`,
"unless the planner finds a better-scoped module". It stays there: it is the module that already
holds the library's uint16-granularity colour comparisons, and moving it would add a module for
two functions. Its module docstring and the AGENTS.md line describing it (plan 07) are widened to
say it also owns the firmware-effect palette rule.

**Only MORPH changes (D-19).** FLAME and SKY with no palette, and every explicit palette, keep
their current bytes; five golden payloads captured from the unmodified `set_effect()` prove it.

**The derived palette goes through the validator (review L131@92a657d, maintainer item
L543@92a657d).** `set_effect()` still constructs `MatrixEffect(...)` first, so a bad argument
raises before any read. It then rebuilds the effect with `dataclasses.replace(effect,
palette=<derived>)` instead of assigning `effect.palette` after construction. `replace()` reruns
`MatrixEffect.__post_init__`, whose palette check delegates to `validate_effect_palette()` from
Task 2 onwards, so the "at most three generated colours" invariant is enforced by the same rule as
a caller's palette rather than being implicit. `from_device` is an `InitVar` with a default, so
`replace()` needs no extra argument (the planner confirmed this on Python 3.10).

**The emulator this plan runs against.** `uv.lock` pins lifx-emulator-core **3.7.0**; this phase
bumps nothing and adds no Thread emulation. The planner verified each emulator behaviour the tests
below rely on against the installed 3.7.0 package and a live in-process 3.7.0 server on
2026-09-23: `Light.SetColor` repaints every pixel of every tile (`SetColorHandler` in
`handlers/light_handlers.py`), so `set_matrix_colors(0, [c] * n)` on the one-tile
`d073d5000007` leaves `get_all_tile_colors()` holding one distinct colour; `Tile.SetEffect` stores
`palette[:palette_count]` and `Tile.GetEffect` reports it back with the same count
(`tile_handlers.py` `SetEffectHandler` / `GetEffectHandler`), so an explicit three-colour MORPH
reads back three colours and a palette-less MORPH reads back `palette is None`; the library's
products registry gives both `d073d5000007` (product 55) and `d073d5000101` a 2500 K to 9000 K
range; and a `drop_packets` scenario suppresses the packet before the server sends any ack or
reply, so a dropped Get64 surfaces as `LifxTimeoutError`.
</objective>
