Add `_load_probe_alias_map(path: Path) -> dict[str, str]` to
`.planning/scripts/ipv6_thread_probe.py`, mirroring the contract of
`.planning/scripts/measure_merged_discovery.py:731` exactly rather than re-deriving it (D-09).
It derives the repository root as `Path(__file__).resolve().parents[2]`, resolves the supplied
path through `expanduser().resolve()`, and raises `ValueError("--alias-map must be outside the
repository")` when the resolved path is the repository root or has it among its parents. It then
loads the file as JSON, raises on anything that is not a non-empty object, normalises every key
through `Serial.from_string(raw).to_string()`, validates every value through the shared
`validate_alias()`, and raises on a duplicate normalised serial. Add
`from lifx.protocol.models import Serial` to the library import block and `validate_alias` to
the existing `measurement_support` import, both at module scope, since ruff's `PLC0415` rule is
per-file-ignored for `.planning/**` but module-scope imports remain this repository's
convention.

Add one module-level compiled pattern, `_ADDRESS_LITERAL_PATTERN`, beside the existing
`_ULA_NETWORK` constant. It is a single alternation with the **IPv6 branch first** and the IPv4
branch second:

- The IPv6 branch matches two to seven colon-terminated groups of up to four hex digits followed
  by an optional final component that is **either** a dotted-quad **or** a group of up to four
  hex digits, with the dotted-quad alternative written first inside that optional group, plus an
  optional trailing zone suffix captured separately as a percent sign followed by interface-name
  characters. It is bounded by lookarounds rejecting a neighbouring hex digit, colon or dot.
- The IPv4 branch matches four dot-separated groups of one to three digits, bounded by
  lookarounds rejecting a neighbouring digit, letter or dot so a longer dotted token is not
  partially matched.

One pattern rather than two, and IPv6 first rather than second, is load-bearing rather than
stylistic. `discovery.py:432` canonicalises an IPv4-mapped IPv6 record to `::ffff:<IPv4>` and
retains it as unusable diagnostic evidence, so that token really does reach the transcript. Two
sequential passes with IPv4 first rewrite the dotted tail and leave the IPv6 pass to match only
the `::ffff:192` prefix, emitting a corrupted token that is neither the source address nor a
valid pseudonym. Regular-expression alternation is ordered and `re.sub` scans left to right
once, so a single pattern whose IPv6 branch is tried first and whose dotted-quad tail is tried
before the hex tail consumes `::ffff:198.51.100.4` in one match. This was checked against the
staged-diff backstop in `17-03-PLAN.md`: that gate was confirmed to reject the literal residue
`::ffff:192`, so the corruption fails loudly if this ordering is ever undone.

Add a module-level mapping `_REDACTION_PREFIX_BY_CLASS` from each `classify_address()` label to
its reserved documentation sub-range, so the reservation is one readable table rather than a chain
of conditionals: `IPv4` to `192.0.2.`, `GUA` to `2001:db8:1::`, `IPv6-other` to `2001:db8:2::`,
`ULA` to `2001:db8:3::`, and `link-local` to `2001:db8:4::`. Those five values plus the IPv4-mapped
`::ffff:192.0.2.` form below are D-11's table exactly, as amended a second time on 2026-09-08, and
they are what amended AC-21 checks. Do not substitute a different range for any of them.

**Every IPv6 sub-range sits inside `2001:db8::/32`, and that is the correction A5 made.** The first
amendment sent `ULA` to `fd00::` and `link-local` to `fe80::` on the reasoning that those forms look
like what they replace. They are not documentation ranges: `fd00::/8` is the locally-assigned half
of operational Unique Local space (RFC 4193) and `fe80::/10` is operational link-local space
(RFC 4291). A pseudonym drawn from an operational range is not a pseudonym in the sense AC-22 needs,
it is a different real address, and the concrete harm was in the staged-diff backstop, which
whitelisted both forms as safe output: `fe80::1`, exactly the kind of gateway packet-source address
this probe prints, was accepted. Only `2001:db8::/32` (RFC 3849) and `192.0.2.0/24` (RFC 5737) are
reserved for documentation. With the whole table inside them, **any `fd00::` or `fe80::` token in a
staged diff is a leak by definition**, which is what makes the `17-03-PLAN.md` and `17-04-PLAN.md`
backstops exact rather than approximately safe. A reader loses nothing: a redacted link-local
address is still identifiable as link-local from the probe's own message text and from its preserved
zone suffix, not from its literal.

Add `class _TranscriptRedactor` with a constructor taking the loaded alias mapping and a single
public method `redact(self, text: str) -> str`. Its docstring must state that substitution is a
whole-text replace rather than a per-field one, because mDNS instance names and SRV target
hostnames both embed the serial and a per-field approach leaks through any field nobody thought
to cover (D-10).

`redact()` runs exactly two single-pass `re.sub()` scans, in this order, and never re-scans its
own replacement text. Doing it as two forward-only passes is what makes double substitution
impossible when one pseudonym happens to prefix another live value; that hazard is the SPEC's
`ordering / R8` backstop edge, and the operator staged-diff grep in `17-03-PLAN.md` and
`17-04-PLAN.md` remains its backstop rather than its only defence.

produces, the colon-separated six-octet form, and the hyphen-separated six-octet form. The

parsing match, classify it with the existing `classify_address()` (never a second classifier),

**The contract, stated exactly, and it is the one AC-21 locks.** SPEC amendment A4 replaced
AC-21's original "documentation-range equivalent of the same class" with a **sub-range
reservation**: a literal inside a documentation range, drawn from a sub-range reserved for that
address's source class, no two source classes sharing a sub-range, stably within a run. A5 then
corrected the table A4 settled on, moving all four IPv6 classes inside `2001:db8::/32`. D-11 was
amended alongside both and now names the table this task builds, value for value. Build to that
criterion; there is no deviation here to caveat and no clause of AC-21 or D-11 this design falls
short of.

What the reservation gives is the property the criterion exists to protect: the distinction R1's
refused case demonstrates, that the cached records were of a class the selector rejects, survives
into the committed transcript, because a reader recovers it from the reserved sub-range.

What it does not give, and must not be described as giving, is a `classify_address()` round trip.
Running the shipped classifier over the replacements shows why: `classify_address("192.0.2.1")`
returns `IPv4` and round-trips, but every one of the four IPv6 replacements returns
**`IPv6-other`**, because `2001:db8::/32` is reserved for documentation and Python's `ipaddress`
reports `is_global` False for it, `is_link_local` False for it, and it is not inside `fc00::/7`.
So `classify_address("2001:db8:1::5")`, `classify_address("2001:db8:2::5")`,
`classify_address("2001:db8:3::5")` and `classify_address("2001:db8:4::5")` all return the same
label. There is no documentation-safe IPv6 range that classifies as `GUA`, `ULA` or `link-local`,
so a round-trip contract for those classes is unsatisfiable by construction rather than by
oversight, which is why A4 exists and why A5 could tighten the table without losing anything.
Nothing in this phase re-classifies redacted text, so nothing depends on the round trip.

State this in `_TranscriptRedactor`'s class docstring, naming the four `2001:db8:` sub-ranges that
all collapse to `IPv6-other` under re-classification and saying that the reserved sub-range, not the
classifier, carries the class information after redaction. A4 requires that docstring sentence by
name, and A5 changes which sub-ranges it must name. The docstring must also state that the
redactor emits no `fd00::` or `fe80::` form, because that is the property the staged-diff backstops
in `17-03-PLAN.md` and `17-04-PLAN.md` rely on to treat such a token as a leak by definition.

`192.0.2.0/24` and `2001:db8::/32` are the documentation ranges this repository already treats
as safe; `tests/test_network/test_mdns/test_phase_contract.py:371-386` enforces exactly that for
documentation surfaces. Do not invent alternative ranges, and specifically do not reach for
`198.51.100.0/24` or `203.0.113.0/24` to widen the IPv4 ceiling. Two subnets of headroom would
