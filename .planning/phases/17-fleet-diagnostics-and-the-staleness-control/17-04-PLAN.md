<objective>
Measure advertisement staleness against one WiFi bulb using the identical protocol THREAD-04 ran
on Thread, and commit the session manifest and staleness JSONL under `17-EVIDENCE/`.

Purpose: DISC-04. v2.0 recorded one Thread trial and no control, so the 4140 to 4200 second
disappearance-to-expiry interval and the 69.4 second restoration figure both stand alone. A
same-protocol WiFi arm is what turns them from an observation into a comparison.

Output: `17-EVIDENCE/14-MANIFEST.json` and `17-EVIDENCE/14-STALENESS.jsonl`, both produced by the
unmodified `thread_revalidation.py` and both carrying `session_id` `seed-002`.

**Filenames (D-13, as amended).** The tool hardcodes its evidence filenames as module-level
constants at `.planning/scripts/thread_revalidation.py:310-321`, literally `14-MANIFEST.json` and
`14-STALENESS.jsonl`, and they are not parameterised by `--session-dir`. The WiFi session
therefore lands at `17-EVIDENCE/14-MANIFEST.json` and `17-EVIDENCE/14-STALENESS.jsonl`: a `17-`
prefix on the directory, the tool's own `14-` prefix on the files. Do not rename them after the
run and do not add a rename step. `reload_staleness_events()` and the same-alias resume check in
`_cli_staleness()` both read those literal names back, so renaming would break the resume
guarantee AC-15 exists to prove. Do not modify `thread_revalidation.py` -- **superseded
2026-09-08 for exactly four operator-authorised changes, and no others:** (1) the WiFi staleness
poll's `discover()`/`discover_mdns()` call site now takes an explicit 45s timeout via a new
module-level constant, `lifx.const.DISCOVERY_TIMEOUT` itself and every other call site are
untouched; (2) `elapsed_s` on each staleness poll is now the measured wall-clock time since the
experiment started rather than the nominal `poll_index * interval_s` schedule (the absolute-cadence
scheduling target itself is unchanged); (3) `run_staleness_experiment`'s restoration wait now closes
on the first discovery leg to report present (OR, not AND) and separately, boundedly, keeps polling
for the other leg, recording each leg's own elapsed time in two new nullable row fields,
`restoration_discover_s` and `restoration_mdns_s`; (4) the manifest inventory schema now accepts
`InfraredLight`/`HevLight` entries with real evidence (previously rejected outright), since the
operator's fleet includes both. All four are committed as separate commits on top of this branch;
the v2.0 committed evidence (`14-STALENESS.jsonl`, `14-MANIFEST.json`) still reloads/validates
unchanged under the new schema. Every OTHER constraint in this plan that assumes an unmodified
tool -- including the `THREAD-REVALIDATION-MODIFIED` automated gate below, the "unchanged in the
working tree" verification steps, and every line-number citation against the pre-change file --
predates this authorisation and needs reconciling (a replan or a targeted line-number refresh)
before this wave actually runs.

**Hardware gate (D-21, as amended on 2026-09-08).** If the WiFi run cannot be performed, MDNS-10
still ships from waves 1 and 2 and DISC-04 stays open as a requirement, carried forward the way
THREAD-01 to THREAD-05 carried from v1.1 into v2.0. Recording it as a closed gap was explicitly
rejected: that would launder an unrun experiment as a completed one, which the roster gate exists
to prevent. The amended decision states the same rule for the Thread arm, so neither arm's failure
is authorised to close the other's requirement.

**This plan now holds wave 4 alone, and that is a change (Codex, HIGH, uncontested).** It used to
share wave 3 with `17-03-PLAN.md` on the grounds that the two are file-disjoint in what they write.
That was the wrong test. Both stage into the same git index and both inspected the whole staged
`17-EVIDENCE/` directory, so a concurrent run in one worktree could inspect or commit the other's
staged artefacts, and this plan's power-on-failure recovery moved the entire `17-EVIDENCE/`
directory outside the repository, which could have relocated `17-03-PLAN.md`'s already committed
transcript. D-21 as amended records that file-disjointness alone does not make the two arms safe to
run concurrently.

**The resolution chosen, and why.** Three changes, all here or in `17-03-PLAN.md`. First, the two
plans are **serialised**: the probe transcript takes wave 3 and this trial takes wave 4, so only
one of them ever has a staged index. Serialising costs nothing operationally, because D-20 puts
both in one operator sitting either way, and running the seconds-long probe before the up-to-three-hour
trial gets the sitting's irreversible commit out of the way before the long wait. Second, **every
staged inspection here names this plan's own two files** rather than the shared directory, so it
cannot read or judge the transcript. Third, the **recovery path no longer moves the evidence
directory**: it preserves only the two tool-owned files as an intact attempt bundle, which is what
makes a retry clean without touching anything another plan owns.

Serialising does not couple the arms' outcomes. `17-03-PLAN.md` exiting with R4 open is a
completion, so this plan still runs; the dependency is on that plan finishing, not on it
succeeding.

**Sequencing (D-20), stage two of three.** This plan and `17-03-PLAN.md` together are still D-20's
hardware stage, the single operator sitting. That stage now spans two execution waves for index
serialisation, exactly as D-20's no-hardware stage spans waves 1 and 2 for file serialisation, and
`17-05-PLAN.md` moves to wave 5 behind it. Five tasks sit here rather than three because three of
them are checkpoints; splitting the hardware work across further plans would break D-20's
single-operator-sitting design and AC-16's one-device-at-a-time rule.
