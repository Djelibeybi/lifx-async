**Hardware gate (D-21, as amended on 2026-09-08).** This plan needs real Thread hardware, which is
not probeable from an automated environment. D-21 originally authorised partial delivery only when
the WiFi run could not be performed, which left this plan's "no thread hardware" exit with no
decision behind it. As amended, D-21 covers both arms: each can fail independently, and an arm
that cannot run leaves its evidence requirement **open rather than closed**. So a Thread fleet that
cannot be reached leaves **R4 open**, carried forward the way THREAD-01 to THREAD-05 carried from
v1.1 into v2.0, while MDNS-10's code and tests ship from waves 1 and 2 regardless. Nothing in this
plan, its SUMMARY or the phase may describe R4 as satisfied without a committed transcript.

**Wave 3 is this plan alone, and that is a change (Codex, HIGH, uncontested).** This plan and
`17-04-PLAN.md` used to share wave 3 because they are file-disjoint in what they write. That was
the wrong test for these two. Both stage into the same git index and both inspect the staged
`17-EVIDENCE/` directory, so run concurrently in one worktree each can inspect or commit the
other's staged artefacts, and `17-04-PLAN.md`'s power-on-failure recovery used to move the whole
`17-EVIDENCE/` directory outside the repository, which could have relocated this plan's already
committed transcript. D-21 as amended records that file-disjointness alone does not make the two
arms safe to run concurrently.

**The resolution chosen, and why.** Both, belt and braces. First, the two plans are **serialised**:
this plan holds wave 3 and `17-04-PLAN.md` moves to wave 4, so only one of them ever has a staged
index. Serialising costs nothing operationally, because D-20 puts both in one operator sitting
either way, and this is the short arm: a records-stage probe sweep is seconds while the staleness
trial blocks for up to three hours, so running the probe first also gets the sitting's risky commit
out of the way before the long wait. Second, **scoping**: every staged inspection in this plan
names this plan's own file rather than the whole evidence directory, so even under an unexpected
concurrent run it cannot read or judge another plan's artefacts. Isolated worktrees were considered
and rejected: two worktrees would need two commits merged by hand into one branch, which adds a
merge step to the one part of the phase where a mistake is unrecoverable.

Serialising does not couple the arms' outcomes. If this plan exits with R4 open, it has completed;
`17-04-PLAN.md` still runs. The dependency is on this plan finishing, not on it succeeding.

**Sequencing (D-20), stage two of three.** This plan and `17-04-PLAN.md` together are still D-20's
hardware stage, the single operator sitting. That stage now spans two execution waves for index
serialisation, exactly as D-20's no-hardware stage spans waves 1 and 2 for file serialisation. The
stage ordering D-20 specifies is unchanged.
