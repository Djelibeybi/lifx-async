## Permanent residual: multi-dot owner forms (cross-AI review, adjudicated MEDIUM)

The plan-review pass found that this plan's earlier threat entry T-16-04 claimed a mitigation
the design does not deliver. The claim was *"the private delegate never re-applies the
non-idempotent helper"*. Verified false against source: the delegate reaches addresses through
`_addresses_in_order()` (discovery.py:359) -> `records_for()` (discovery.py:338) ->
`_normalise_dns_name(owner)` (discovery.py:320). The helper IS re-applied inside the delegate's
own call chain.

**What that does and does not break.** For an owner carrying a single trailing dot, the
re-application is a no-op, because `_normalise_dns_name` is idempotent on an already-normalised
value: `"host.local."` normalises once at discovery.py:659 to `"host.local"`, and normalising
that again returns it unchanged. Guard key and lookup key agree, and **every SPEC acceptance
criterion still holds**: requirement 1's criteria and all four of its `## Edge Coverage` rows
(adjacency, empty, encoding, ordering) cover bare, trailing-dot, uppercase and mixed-case forms
only. A multi-dot form is never demanded.

For an owner carrying two or more trailing dots the two keys diverge: `"host.local.."`
normalises once to `"host.local."`, the guard uses that key, and the lookup normalises it again
to `"host.local"` and misses. The instance stays pending and is re-queried, which is exactly the
failure mode D-01's rationale describes for the naive one-line fix, confined to a form the SPEC
does not cover.

**Resolution: wording plus a recorded residual, not a refactor.** T-16-04 is reworded below to
state only what is actually mitigated, the residual is carried in `must_haves.key_links`, and
Task 1 adds one sentence to `_normalise_dns_name()`'s docstring naming its non-idempotence so a
future contributor does not treat it as a safe canonicaliser. D-02 declines to widen the helper,
so the residual is permanent by decision; this makes it a documented permanent residual rather
than an undocumented one.

**Explicitly not adopted:** the review's suggested normalised-only-internals refactor
(`_records_for_normalised()` and `_addresses_in_order_normalised()` variants, with public
lookups normalising once and delegating). It would close the multi-dot case, but no acceptance
criterion fails without it, it widens the diff across three more methods on the same fail-closed
path this phase is repairing, and widening the owner-form invariant to multi-dot forms is a
scope change the SPEC does not ask for. Recorded here so the decision is visible rather than
silent. If a later phase wants the multi-dot case genuinely closed, that refactor is the shape
to reach for.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| mDNS responder -> `_LifxRecordCache` | Untrusted DNS wire data crosses here. Owner names, SRV targets and address records arrive from any host on the local link, including a Thread border router answering for devices it does not own. |
| `_LifxRecordCache` -> caller (`discover_mdns()`, `find_by_*`) | A selected address becomes a socket destination. A wrong answer here directs traffic at a host the cache never validated. |
| Committed test fixtures -> git history | The AGENTS.md privacy rule binds here. A real serial, MAC, IP or hostname committed once persists in history. |

ASVS level 1, blocking on `high`.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-16-01 | Spoofing | `selected_address_for()` owner argument | high | mitigate | The defect this plan closes: a hostile or malformed responder supplying `host.local.` currently bypasses all five fail-closed guards and still receives an address. Task 1 routes the public entry point through `_normalise_dns_name()` so the guard set and the record lookup key on one identity. Task 2's parametrised matrix asserts the equivalence across bare, trailing-dot, uppercase and mixed-case forms, and its encoding test drives a casefold-sensitive owner into an owner-keyed guard so a lookup that merely succeeds cannot stand in for guard agreement. |
| T-16-01b | Spoofing | Empty and DNS-root owner names | high | mitigate | Verified reachable during the cross-AI plan review, not merely theoretical: the root name and the empty string both normalise to the empty string, ingest keys a root-owner address record under it (discovery.py:400), and no guard rejected it, so `selected_address_for("")` and `selected_address_for(".")` both returned a cached address. A responder advertising a root-owner address record could therefore hand a caller a socket destination under a name that identifies nothing. Task 1 adds `not owner` as the first term of the shared predicate, so both call sites refuse it; Task 2 proves it fail-closed by asserting the record is present in the cache while the selection still returns `None`. |
