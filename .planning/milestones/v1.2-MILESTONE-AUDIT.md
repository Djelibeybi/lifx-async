## Integration

Eight seams checked, six clean, two findings at one seam.

### Clean

1. **Generated-data pipeline.** `data/themes.jsonl` to
   `scripts/generate_theme_data.py` to `schema.py` to `data.py` to `library.py`
   to the public API. Regeneration is byte-idempotent. No reference to the old
   in-package `lifx.theme.generator` path survives in source, tests, docs or CI;
   the CI regen-and-diff gate uses the `scripts/` path.
2. **Slug single-sourcing.** Exactly one `derive_slug`, in `src/lifx/theme/slug.py`.
   Both `library.py` and `schema.py` import that one definition. No second copy.
3. **Phase 6 identity fields against Phase 7 disposition fields.** A
   caller-built `Theme()` gets `None` for all five identity fields, `Theme`
   stays hashable, and `palette_equals()` ignores every identity field.
4. **Taxonomy coverage.** All 169 resolvable keys are either listed under their
   category or are one of the 3 `renamed` aliases, which are deliberately
   skipped to avoid double-listing. All 9 deprecated keys carry a `replaced_by`
   that resolves. Both alias pairs share palette storage by identity.
5. **Docs drift test.** `tests/test_theme/test_docs_catalogue.py` passes; the
   published counts and all nine category names match the live library.
6. **API surface.** `__all__` is 6 names. `schema` and `Canvas` are importable
   but unexported, consistently. All four consumer flows complete offline.

### INT-01: ceiling determinations superseded by the resync

`08-CEILING-DETERMINATIONS.json` selects on `literal_palette_length: 16` from
`data/themes.jsonl`. That predicate now yields zero rows: no shipped record has
a 16-colour palette.

This is supersession, not regression. The Phase 8 palettes were measured
off-device, where the protocol ceiling truncates at 16 colours. Phase 9's resync
replaced them with full palettes from an internal LIFX HTTP API endpoint, which
returned the true palette for exactly those 25 themes.

Verified directly: the 25 determination slugs are exactly the pre-resync
`lifx-app` 16-colour set, equal in both directions with zero difference. All 25
still exist and are still `lifx-app`. Their current lengths run 18 to 68.

FIDELITY-01 asks for "their true length, **or** a documented finding that no
device-based method can supply it". Phase 8 could only reach the second branch.
Phase 9 satisfied the first. The requirement is met more strongly than at Phase
8 close, and the file's finding remains true as written, because the resync used
a non-device method.

What is stale is the bookkeeping: a committed artefact declares a provenance
rule that no longer describes its stated source, and FIDELITY-01's own text
bakes in a selection clause that now selects nothing.

### INT-02: the guard was never connected

`test_documentation_counts.py` lives only under
`.planning/phases/08-hardware-fidelity-validation/tests/`, never under `tests/`,
so the main suite does not collect it. Run directly it reports 3 failed, 1
passed. Had it been collected, the resync would have failed CI and INT-01 would
have surfaced in August rather than at milestone close.

### INT-02 closed — `7ae518f`, with the finding corrected

The audit above said the guard "was never connected", implying it should have
been. That is not right, and the correction matters for anyone reading this
later.

`pyproject.toml` sets `testpaths = ["tests"]`, so the Phase 8 harness was never
intended to be collected: it is phase evidence, not shipped test code. It also
cannot be repaired in this repository. It depends on `.claude/theme-capture/`,
which was untracked and has since been removed along with the TOOL-01/02/03
withdrawal to `lifx-theme-resync`, plus ADB and physical hardware. Targeted
directly it now reports 97 failed, 155 passed, not the 3 failures the audit
cited from one file.

So the real gap was narrower than stated: no *connected* guard existed for the
invariant worth keeping. One now does.

`tests/test_theme/test_ceiling_supersession.py` pins the 25 slugs as an explicit
literal and asserts each still resolves, is still `lifx-app`, and still ships
above `MAX_PALETTE_COLORS`. It reads only shipped data, never `.planning/`,
because phase directories move at milestone close. 51 tests, and
mutation-checked: clipping `mondrian` back to 16 colours fails it.

The Phase 8 harness is left in place as archived evidence.

### Phase 7 sign-off — finding withdrawn

The audit listed this as needing operator sign-off. That was wrong, and the
error is worth recording rather than quietly deleting.

The sign-off had already happened through the designed mechanism.
`/gsd-verify-work` reads the `human_verification:` array from VERIFICATION.md
frontmatter, persists each entry as a numbered UAT scenario, and flips the
status when they pass. That is exactly what happened: `c85167f` (13:47) created
the two scenarios and set `status: human_needed`; `f002cd4` (14:10) closed UAT
with both at `result: pass` and set `status: passed`. `07-UAT.md` holds the
record, including the operator rejecting test 1's first attempt over the leaked
internal `v1.2` label.

What misled the audit: the VERIFICATION.md *body* still carried its pre-UAT
`Status: human_needed` line while the frontmatter correctly read `passed`. The
body line is now reconciled.
