## Warnings

### WR-01: API reference example claims `evening` is in category `Moods`; it is `Library`

**File:** `docs/api/themes.md:49`
**Issue:** The live-reference example prints identity metadata with a wrong expected
output:

```python
theme = ThemeLibrary.get("evening")
print(theme.slug, theme.name, theme.category)  # evening Evening Moods
```

Verified against the shipped data: `THEMES["evening"].category == "Library"`
(`evening` is one of the 28 pre-v1.2 orphans, disposition `library-only`). The
comment contradicts the category system this very page documents, three paragraphs
above a table that places `evening`'s category (`Library`, 28) correctly. Unlike the
migration page, this page is not a dated record — it is current-state reference.
Plan 07-03 ("correct the two stale theme doc sites") touched this file but this
stale claim survived.

**Fix:** Correct the comment, or use a lifx-app theme so the example also shows an
app category:

```python
theme = ThemeLibrary.get("evening")
print(theme.slug, theme.name, theme.category)  # evening Evening Library
```

### WR-02: A self-referential `replaced_by` passes the generator and every test sweep silently

**File:** `scripts/generate_theme_data.py:357-365` (cross-record pass); `tests/test_theme/test_library.py:629-633` (resolution sweep)
**Issue:** The cross-record pass only requires `replaced_by in seen_keys`, and
`seen_keys` includes the record's own slug and its own aliases. A future data edit
such as:

```json
{"slug": "foo", "disposition": "deprecated", "replaced_by": "foo", ...}
```

validates, emits, and ships — proven empirically: `validate_records()` and
`emit_data_module()` both accept a record whose `replaced_by` names its own slug,
emitting `disposition="deprecated", replaced_by="foo"` on `foo` itself. The
test-side sweeps close neither gap: `test_every_replaced_by_resolves` asserts only
`record.replaced_by in THEMES`, which a self-reference satisfies. The SPEC permits
chains onto *another* deprecated key; a key deprecated in favour of itself is not a
chain, it is semantically incoherent data that would surface directly on the public
`Theme.replaced_by`, and user code following successor links would loop. Zero exist
today, so this is a robustness gap, not a live defect.

**Fix:** One line in the cross-record pass (and/or a mirror assert in the
`TestDispositionSurfacing` sweep):

```python
for line_number, record in records:
    replaced_by = record.get("replaced_by")
    if replaced_by is None:
        continue
    if replaced_by == record["slug"] or replaced_by in record.get("aliases", []):
        raise _fail(
            line_number, record,
            f"replaced_by {replaced_by!r} names the record itself",
        )
    if replaced_by not in seen_keys:
        ...
```

## Info

### IN-01: Atomic-write docstrings overclaim; a killed run leaves an importable stray `.py` inside the package

**File:** `scripts/generate_theme_data.py:9-11, 570-577, 583`
**Issue:** The module and `main()` docstrings state an interrupted run leaves "no
stray temp file behind". That holds for every Python-level exception (the `finally`
covers it, and the tests prove it), but not for SIGKILL or power loss between
`mkstemp()` and cleanup: a `tmpXXXXXXXX.py` file would remain inside
`src/lifx/theme/` — an importable module in the package tree that a subsequent wheel
build would ship. Low likelihood, but the docstring's claim is broader than the
mechanism.
**Fix:** Either narrow the claim ("any run that fails with an exception"), or make
`main()` sweep stale leftovers before generating:

```python
for stale in OUTPUT_PATH.parent.glob("tmp*.py"):
    stale.unlink()
```

### IN-02: `get_by_category()` docstring hardcodes the nine category names — the rot vector this phase just removed

**File:** `src/lifx/theme/library.py:180-185`
**Issue:** The docstring enumerates "Archives, Art Series, Holidays, Library (…),
Moods, Music, Nature, Play and Space". Accurate today, but it repeats the failure
mode Phase 7 was created to fix (the retired docstring advertised a `time` category
that never existed). A resync that adds or renames an app category updates the data
and fails the pinned `test_exact_sorted_list`, but nothing ties this prose list to
the data.
**Fix:** Add one assert to `TestGetCategories` binding the docstring to the data
(e.g. every name from `get_categories()` appears in
`ThemeLibrary.get_by_category.__doc__`), or trim the enumeration and point at
`get_categories()` instead.

### IN-03: `docs/api/themes.md` count table and 166/168 figures have no CI tie

**File:** `docs/api/themes.md:18, 36-39, 55-65`
**Issue:** The page correctly refuses to reproduce the theme inventory "where it
rots on every resync", yet pins the total (166/168) and a per-category count table
immediately below. Unlike the migration page, which declares itself a dated record,
this is live reference; nothing fails when the data changes. All values verified
correct today.
**Fix:** Either add the same dated-record framing the migration page uses, or add a
lightweight docs test asserting the table matches
`Counter(r.category for r in {id(r): r for r in THEMES.values()}.values())` so a
resync fails loudly.
